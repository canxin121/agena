一条消息,从按键到工具调用,在 agena 里走过哪些层

在 TUI 里发一句话、回车、AI 开始打字、还调了工具——这条路径在代码里横穿 4 个 crate 层:键盘事件经 tui-platform → tui-app 进入,再由 tui-app::app_backend(旧 agena-tui-backend 已并入)经 application 的 SessionExecutionCommandService trait 直接进入 runtime——旧的 ApiCommand::SubmitMessage → dispatch_command 中转已被剥掉。随后在 SessionManager::run_until_stable 里进入一个 agentic loop:发请求 → 收流 → 有 tool_use 就执行 → 把结果投影成 tool_result 再发,直到模型不再要工具。AI 的输出再经 storage 的事件广播流回 transcript 渲染。下图是这条信号的完整路径,所有锚点验证于 HEAD c65c307c。

图 2 · Agentic 循环

为什么一次工具调用会"多发一轮"

run_until_stable(replies_execution.rs:256)不是"调一次 API 就完",而是一个 loop,每轮迭代处理一个阶段。工具的 tool_use part 不会立刻变成独立消息——执行结果内联写回同一个 part 的 Operation,下一次请求模型时由 build_prepared_prompt(prompt_window.rs:788)→ project_persisted(wire_message.rs:147)投影成 wire 的 tool_result。顺序如下:

  1. 并发守卫注册

    start_registered(ExecutionSource::User, NewTurn) 防重入;一条用户消息 = 一个 run marker,多轮模型请求共享同一 marker,content["rounds"] 记录每轮。

  2. 检查取消 · 注入新输入

    control.cancel(CancellationToken)→ 终止;drain_steer_input(replies_state.rs:526)把运行中新到的用户消息并进当前 run。

  3. blocked?→ 挂起

    session.blocked()(等待权限/用户输入)→ 切 ExecutionPhase::AwaitingInteraction 并在 wait_for_interaction_after(execution_registry.rs:116)让出,直到批准信号唤醒。

  4. doom-loop 检测

    doom_loop::detect,最多恢复 2 次,每次注入 DOOM_LOOP_RECOVERY_PROMPT。

  5. 有 pending tools?→ 执行

    resolve_pending_tools(:1477)把 batch 分成 Ready / AwaitingPermission / Sequential → preflight 权限(aggregate_permission_outcome :2155)→ ToolExecutor 执行(prepare_invocation → execute_invocation_detailed_with_prepared_shell)→ apply_tool_success_with_rules(:3015,直接读 execution.view)写回 Operation part → continue 回第 2 步再发一次模型。

  6. !model_requested?→ 收尾

    发 agent.stop 钩子(可被插件改写/续命)→ return Ok(session)。

  7. 预算校验

    model_turns_taken 超 DEFAULT_MAX_MODEL_TURNS=500 → ModelTurnBudgetExhausted;另有 follow-up(4 次)与截断续写(4 次)预算。

  8. run_model_turn

    构造 SessionRunRequest → SessionProcessor::run_turn(run.rs:138,注意新签名带 &ProviderRegistry 参数):provider_registry.complete_stream(run.rs:170)发起请求,loop stream.next() 把 TextDelta / ToolCallDelta / ThinkingDelta / Completed 累积进 parts;结束后 should_continue_turn(:97)决定是否再循环——优先级:有 pending 工具 > follow-up > 截断 > Stop。

暂停/恢复是"暂停循环",不是"结束"。工具要批准时,PermissionRequest 被写进 tool part 的 authorization,part 置 Pending,session 派生后 blocked()==true。用户批准走 reply_permission_dispatch(replies.rs:988)→ 记 reply → signal_interaction 唤醒挂起循环 → 以 ExecutionSource::PermissionReply 重新进入 run_until_stable,工具继续执行、模型继续生成。

图 3 · 渲染回流

AI 的输出怎么流回屏幕

两条并行管道,都汇到 transcript。琥珀线是流式通道(核心):runtime 每写一个 part 都经 storage 广播 SessionChange,backend 订阅后转成 RuntimePresentationEvent。绿线是一次性结果通道:提交完成时 backend 返回执行快照。两者最终都触发 refresh_session 拉新快照并重绘——但每个 PartUpdated 不会都刷全屏:普通事件只做缓存失效,仅 force_refresh(提交完成、bus 溢出降级)才被 pending_refresh_for park 到 tick 预算;真正重绘靠 on_tick 的 REFRESH_INTERVAL_MS(250ms)门控。

走读笔记

六条读完能少踩坑的结论

  • 一条用户消息 = 一个 run marker。多轮模型请求(工具结果、follow-up、截断续写)共享同一 marker,content["rounds"] 逐轮计数——排查"为什么一次输入调了好多次 API"先看这里。
  • tool_result 不是独立消息。工具输出内联在 tool_call part 的 Operation 里;发给模型的 tool_result 是下轮 prompt 构建时由 build_prepared_prompt(prompt_window.rs:788)→ project_persisted(wire_message.rs:147)投影出来的。改 wire 层时别去存一条假的 tool_result。
  • 权限暂停是"暂停循环",不是"结束"。批准经 signal_interaction 唤醒后以 ExecutionSource::PermissionReply 重新进入 run_until_stable(replies.rs:988 · execution_registry.rs:111)。
  • 流式 UI 靠"失效 + tick 门控刷新"。每个 PartUpdated 都来一个事件,普通事件只做缓存失效、不排队刷新;仅 force_refresh(提交完成 / bus 溢出)被 pending_refresh_for park,由 on_tick 的 250ms 门控消费;真正的打字效果来自每 tick 重画 transcript 状态。
  • 插件错误从不信任插件文本。ToolError::Plugin 用 host 模板重建 Failure,诊断截断清洗(tool_registry.rs:478);插件工具超时默认 300s(interactive/task 24h),内建 shell 靠 watchdog 线程强制超时。
  • 循环有预算,不是无限。max_turns 默认 500,doom-loop 恢复 2 次,follow-up 与截断续写各 4 次;provider 层另有重试 / 断路器 / 流重放(registry/completion.rs:824)。
