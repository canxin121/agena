### 让回答更容易理解

富内容直接属于回答。普通解释用文字，只有结构能帮助理解时才使用图形表达。

#### 建议的实施顺序

1. **P0 · 先统一内容契约**

   让文字与富内容按顺序出现在同一条回复中，不创建独立应用。

2. **P1 · 做好 Web 与终端表达**

   Web 使用清晰的间距与层次；终端保留相同的信息、标题和数据。

3. **P2 · 按需了解，适度使用**

   先读简短指南，再查询具体内容块的结构与示例。

#### 两种能力，各司其职

|  | Inline Generative UI | Web Preview |
| --- | --- | --- |
| 目标 | 帮助理解 AI 的回答 | 查看与验证真实项目 |
| 内容 | 步骤、对比、表格与图表 | 项目源码和开发服务器 |
| 执行 | 不运行模型生成的代码 | 经过授权后运行项目 |

#### 内容优先

> 不是每句话都需要卡片。让排版服务于解释，而不是增加界面负担。

#### 这份示例包含

- **内容类型:** 8 种 — 展示完整的受控内容目录
- **展示端:** Web \+ TUI — 同一内容，不同布局

#### 验收重点

| 场景 | 要求 |
| --- | --- |
| 窄屏与长中文 | 自动换行，不挤出消息容器 |
| 复制与导出 | 保留标题、说明与完整数据 |
| 历史回放 | 不发起写入，不重新启动服务 |

#### 为什么不直接生成 HTML？

受控内容块更容易保持样式一致、安全性与终端可读性。复杂可执行页面仍由独立的预览能力处理。
